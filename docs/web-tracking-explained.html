1. Cơ bản: Web tracking khác mobile ở đâu

Nếu bro đã làm iOS/Android/Flutter tracking, chuyển sang web sẽ ngạc nhiên vì 4 điểm:

AspectMobile (iOS/Android/Flutter)Web
Storage SQLite riêng, không giới hạn dung lượng (tính bằng GB) localStorage: 5-10 MB. IndexedDB: có thể vài trăm MB, nhưng browser tự xóa nếu ít dùng
Session Process sống suốt, singleton lâu bền Mỗi reload = reload page, không có singleton. Session phải persist qua localStorage
Screen change ViewController push/pop rõ ràng, framework hook được SPA đổi URL không reload page → phải hook history.pushState monkey-patch
Click UIGestureRecognizer / View.setOnClickListener — có API chuẩn DOM event bubble. Bắt document-level, resolve element_key từ HTML attribute
Kiến trúc mobile vs web — web dễ mất state hơn vì mỗi reload là 1 lần chết

2. Session — dễ sai nhất

Session_id là "1 chuỗi ID nối liền các event của cùng 1 lần user dùng app". Khác từng event `user_id` — user_id giữ nguyên qua nhiều ngày; session_id đổi khi user "quay lại sau 1 khoảng thời gian idle".

Idle 30+ phút → session rotate, event mới stamp session_id mới

2.1 Session lưu ở đâu? Ai xóa nó?

3 loại storage browser cho phép:

StorageCross-tab?Sống bao lâu?Dung lượng
sessionStorage ❌ Chỉ trong 1 tab Đóng tab = xóa ~5MB
localStorage SDK dùng ✅ Share cross-tab Đến khi user clear browser data ~5-10MB
Cookie ✅ Share cross-tab, cross-subdomain Tuỳ expire flag ~4KB

Case 1: User mở 5 tab shopping cùng lúc

User đang so sánh giá — mở /product/A, /product/B, /product/C, /cart, /checkout ở 5 tab. Data team hỏi "user này có 1 hay 5 phiên?"

Nếu SDK dùng sessionStorage: mỗi tab 1 session_id khác → analytics thấy 5 session giả → conversion rate sai (funnel bị chia 5).

Nếu SDK dùng localStorage (đúng): 5 tab đọc cùng 1 key unitrack.session_id → cùng 1 session.

Amazon, Shopify, Booking.com đều dùng localStorage cho session vì user thường mở nhiều tab so sánh sản phẩm. Snowplow JS Tracker cũng thế.

2.2 Khi nào session rotate?

SDK check 3 điều kiện, cái nào xảy ra trước:

  1. Idle timeout: user không tap gì suốt 30 phút → rotate
  2. Manual rotate: app gọi UniTrack.rotateSession() khi login/logout
  3. Storage bị xóa: user clear cookies → cold start = session mới
// SDK logic (session.ts) — 25 dòng cốt lõi
class SessionManager {
  touch() {
    const now = Date.now();
    if (now - this.lastActiveTs >= this.timeoutMs) {
      this.rotate();  // Idle quá lâu → session mới
    }
    this.lastActiveTs = now;
    localStorage.setItem('unitrack.session_last_active', String(now));
  }
}

Case 2: User mở app buổi sáng, đi họp, quay lại buổi chiều

Hành vi user:

  • 08:15 — Vào /dashboard, xem 3 báo cáo
  • 09:00 — Đi họp, laptop khoá màn
  • 14:20 — Mở lại tab, làm tiếp

Data team sẽ có 2 session: ID1 (08:15-08:something) và ID2 (14:20-…). Field previous_session_id ở session 2 stamp = ID1 → BE ghép được nếu cần "same-day journey".

Google Analytics gọi cái này là "returning session". Snowplow gọi là "session_index" (1, 2, 3, …). UniTrack track cả 2 field.

2.3 Case Safari ITP — landmine đặc biệt Nghiêm trọng

Apple từ iOS 14 áp dụng Intelligent Tracking Prevention (ITP):

Safari xóa localStorage nếu user không truy cập domain trong 7 ngày.

Hệ quả: user Safari mở app tuần trước, hôm nay quay lại → session_id đã bị xóa → SDK sinh session_id mới → BE thấy như "user mới hoàn toàn".

Cách mitigate:

  • Server-side reconstruct session từ user_id nếu user đã login
  • Chấp nhận trade-off: session_id chỉ đảm bảo trong ngày dùng, không cross-day
  • KHÔNG dùng cookie 3rd-party (Safari block hoàn toàn)

2.4 Case Private/Incognito mode

🕶️ Chrome Incognito · unitrack-demo.com

localStorage vẫn work trong incognito, nhưng bị xóa khi close tab.

User mở incognito → SDK vẫn tạo session_id → user tap 10 event trong 5 phút → OK, cùng 1 session.
Đóng tab → localStorage bị xóa → lần sau mở incognito = session mới.

Đây là behavior đúng theo intent của user (họ muốn ẩn danh). Không phải bug SDK.

3. Click auto-capture — cần biết delegate

Trên mobile, mỗi Button có OnClickListener riêng. Web thì hàng trăm element có thể click được (button, a, div, span, li, ...). SDK không thể attach handler cho từng element — sẽ dùng event delegation: 1 handler duy nhất ở document, bắt mọi click nhờ event bubble.

Event bubbling — click ở button bubble lên document. SDK chỉ cần 1 listener duy nhất.

3.1 SDK bắt click thế nào?

// auto-capture.ts — chỉ 3 dòng cốt lõi
document.addEventListener('click', (ev) => {
    const target = ev.target;
    const key = resolveElementKey(target);
    UniTrack.track('click', { element_key: key });
}, true);  // capture phase: bắt TRƯỚC handlers của app
Tham số thứ 3 true = capture phase. Không có nó, nếu app code gọi event.stopPropagation() ở button handler thì SDK sẽ không bắt được nữa.

3.2 element_key resolve theo priority

Với mỗi tap, SDK cần đặt tên element để BE hiểu "user tap cái gì". 5 priority từ ổn nhất đến fallback:

PriorityNguồnVí dụ HTMLKết quả
1 data-track-id <button data-track-id="cta_buy_home"> cta_buy_home
2 id <button id="submit-form"> #submit-form
3 aria-label <button aria-label="Đóng modal"> Đóng modal
4 Text content <button>Mua ngay</button> Mua ngay
5 Fallback tagName+class <button class="btn btn-primary"></button> button.btn.btn-primary
Đề xuất cho team dev: luôn đặt data-track-id cho mọi button quan trọng. Không dựa vào text (text đổi theo i18n Vi/En → analytics vỡ) hay class (class refactor liên tục).

Case 3: User tap 1 card sản phẩm — SDK bắt nhầm span text bên trong

HTML:

<div data-track-id="product_card_A123" class="card">
    <h3>Camera FCAM Pro</h3>
    <span class="price">2.490.000₫</span>
</div>

User tap ngay chữ "Camera FCAM Pro" (h3), không tap ra card. Nếu SDK ngu dại chỉ đọc event.target → element_key = "Camera FCAM Pro" (text content h3).

Cách xử của UniTrack: đi ngược lên DOM tree tối đa 8 cấp, tìm ancestor có data-track-id / là <button> / <a> / role="button". Nếu tìm thấy → dùng element_key của ancestor đó.

Hotjar và FullStory đều làm cách này. Không thì mỗi product card sẽ có 5-10 event_key khác nhau tùy user tap trúng phần nào — vô dụng cho analytics.

3.3 Rage click — signal đặc biệt

User bấm 5 lần liên tục "Buy" nhưng không có gì xảy ra (button lag/gãy) — hành vi này gọi là rage click, dấu hiệu bug UX. Analytics tool xịn sẽ:

  1. Deduplicate: chỉ emit event đầu tiên trong 200ms cùng element_key
  2. Đồng thời emit event rage_click riêng với count: 5 cho product team biết fix
UniTrack v0.1.0 chưa dedup rage click — sẽ thêm v0.2.

4. Screen (SPA route) — vấn đề #1 của React/Vue

Web tracker "cổ điển" (Google Analytics UA) chỉ bắt page load — mỗi lần user reload full page. Nhưng SPA (React/Vue/Next) đổi URL không reload page → GA UA mất trắng 90% navigation.

// Truyền thống — mỗi navigate = full page load
User click /products
  → Browser gửi HTTP GET /products
  → Server render HTML
  → Browser load HTML mới → tracker fire "page_view"

// SPA (React Router, Vue Router, ...) — 1 lần load duy nhất
User click /products
  → history.pushState('/products', ...)   ← URL đổi nhưng KHÔNG reload
  → React re-render component
  → Không có tracker event nào fire tự nhiên

4.1 Cách SDK bắt SPA navigation

Monkey-patch history.pushState — trick từ Google Analytics 4:

// auto-capture.ts
const origPush = history.pushState;
history.pushState = function (...args) {
    const ret = origPush.apply(this, args);
    onRouteChange();  // SDK bắt được đây
    return ret;
};

Cộng thêm 2 event nữa:

  • popstate — user bấm nút back
  • hashchange — SPA cũ dùng hash routing (/#/products)

4.2 3 event screen SDK fire

EventKhi nào firePayload chính
screen_viewed Route mới → user thấy screen screen, title
screen_load_completed Ngay sau screen_viewed, đo render time screen, load_ms
screen_exited chưa impl v0.1 User rời screen (chuẩn bị sang route khác) screen, duration_ms

Case 4: Route redirect chain — 3 event khi user chỉ care 1

User click "Đăng nhập" → app chain redirect:

/login → /auth/verify → /dashboard

Chỉ 200ms giữa mỗi bước. SDK sẽ fire 3 event screen_viewed — nhưng user chỉ thực sự "ở" /dashboard.

Cách xử ngành: coalesce window 120ms — chỉ emit event cho route "settle" cuối cùng. Flutter UniTrack có, web v0.1.0 chưa có.

MobiX (Flutter camera app) từng gặp cái này — journey list bị inflate 3× khi user login. Fix bằng coalesce ở NavigatorObserver v1.1.0.

4.3 Screen name — làm sao đẹp?

Mặc định SDK dùng window.location.pathname:

/                           → "/"
/products                   → "/products"
/products/PROD-A123         → "/products/PROD-A123"    ← ⚠️ high cardinality
Cardinality trap: URL có ID sản phẩm/user → mỗi ID là 1 "screen" khác → analytics database phồng nhanh. GA khuyến nghị max 500 unique screen name / property.

Best practice: app dùng UniTrack.setScreen("product_detail") thủ công để override, hoặc BE regex normalize:

/products/([A-Z0-9-]+)  → /products/:id

5. Network + trace_id + CORS — landmine

5.1 SDK bắt fetch/XHR thế nào?

Monkey-patch window.fetch + XMLHttpRequest.prototype.open/send. Mỗi request → SDK ghi lại URL, method, status_code, duration_ms.

Frontend event + Backend log cùng trace_id → dev grep log join 2 phía

5.2 trace_id là gì? Vì sao cần?

Chuẩn W3C Trace Context — 1 header traceparent format:

traceparent: 00-a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6-1122334455667788-01
             │  │                                │                 │
             │  │                                │                 └─ flags (01 = sampled)
             │  │                                └─ span_id (16 hex, 8 bytes)
             │  └─ trace_id (32 hex, 16 bytes)
             └─ version

Frontend sinh trace_id → gắn header → backend đọc header → backend log kèm trace_id → khi có bug, dev grep trace_id=a1b2... trên cả frontend event + backend log = ráp full journey.

Case 5: User complain "Tôi bấm Mua nhưng lỗi" — dev debug thế nào

Không có trace_id:

  • Frontend log: user tap Buy lúc 14:23
  • Backend log: có 50 request /api/orders trong khoảng 14:20-14:25
  • Không biết request nào của user đó

Có trace_id:

  • Frontend event click "Buy" stamp trace_id=abc
  • Frontend event network_error ngay sau đó cũng trace_id=abc
  • Backend log request có trace_id=abc → thấy exception InsufficientBalance
Kubernetes/microservice environment gần như bắt buộc. Datadog, New Relic, Jaeger đều dùng W3C Trace Context.

5.3 CORS — vấn đề pain #1

Browser không cho JS gắn header custom (như traceparent) vào request cross-origin, trừ khi server explicitly allow.

Flow bị chặn:

Browser (unitrack-demo.com) muốn gửi:
  fetch('https://api.other.com/orders', {
    headers: { 'traceparent': '00-abc-...' }  ← Custom header!
  })

Browser tự động gửi preflight OPTIONS trước:
  OPTIONS /orders
  Origin: unitrack-demo.com
  Access-Control-Request-Headers: traceparent

Server phải trả về:
  HTTP 204
  Access-Control-Allow-Origin: unitrack-demo.com
  Access-Control-Allow-Headers: traceparent    ← BẮT BUỘC có!

Nếu không:
  ❌ Preflight fail → fetch không được gửi
  ❌ Console error: "CORS policy: header 'traceparent' is not allowed"
Fail-closed allowlist: SDK không inject traceparent vào mọi request. App phải config tracingAllowlistHosts: ['api.yourapp.com'] — chỉ inject cho host trong list. Empty = không inject → 0 CORS issue.

5.4 Case exclude ingest self — vô hạn recursion

Case 6: SDK track chính request lên SDK server

Không có exclude → recursion:

  1. User tap Buy → SDK ghi event, gọi POST /web-events
  2. SDK network interceptor bắt request POST đó → ghi event "network_request POST /web-events"
  3. Event mới cần gửi → POST /web-events lần nữa
  4. SDK bắt → ghi lại → POST → ...

Cách xử: SDK auto exclude host của endpoint. Nếu endpoint = "https://mobix.asia/api/web-events" → mọi request đến mobix.asia KHÔNG track.

Segment, Mixpanel, Amplitude đều exclude self. Test case classic: nhìn console debugger có network event tăng exponential = quên exclude.

5.5 SSE và WebSocket — không bắt được

EventSource (SSE) và WebSocket KHÔNG đi qua fetch/XMLHttpRequest — SDK không patch được. Điều này bình thường: SSE/WS thường sống lâu (kết nối 30 phút, 1 giờ), không phải "request" theo nghĩa REST.

6. Ops production — 12 case dev hay bỏ sót

6.1 AdBlock chặn SDK Nghiêm trọng

~30% user desktop có AdBlock. uBlock Origin block domain "unitrack.io", "analytics.google.com", ...

Case 7: uBlock chặn SDK bundle load

Nếu bro serve SDK từ CDN thirdparty:

<script src="https://cdn.unitrack.io/web.js"></script>

uBlock check domain → chặn → SDK không load → 0 event.

Cách xử: serve từ same-domain của app:

<script src="/assets/js/unitrack.iife.js"></script>

AdBlock chỉ block domain, không block path — same-domain thoát được ~90% adblock.

Google Analytics 4 vẫn bị block ~35% desktop. Cloudflare Web Analytics chạy same-domain qua reverse proxy → block rate 5%.

6.2 CSP (Content-Security-Policy)

Website có header CSP kiểu:

Content-Security-Policy: script-src 'self'

Sẽ chặn mọi JS ngoài same-origin, kể cả eval, inline script.

SDK nhớ:

  • KHÔNG dùng eval(), new Function()
  • KHÔNG inject inline script vào DOM
  • Nếu bắt buộc từ CDN → CSP cần add domain: script-src 'self' https://cdn.unitrack.io

6.3 Offline queue — user mất mạng khi tap Submit

// Kịch bản
14:00  User tap Submit form
14:00  SDK track event "form_submitted"
14:00  fetch POST /web-events → ❌ Network error (offline)

// SDK behavior
14:00  Retain event trong IndexedDB
14:00  Đợi event 'online' của browser

// User bật WiFi lại
14:05  Browser fire 'online' event
14:05  SDK flush queue → POST 1 batch chứa event từ 14:00
IndexedDB có thể bị browser xóa khi disk full — không đảm bảo 100%. UniTrack cũng dùng navigator.sendBeacon lúc pagehide để force flush trước khi tab close.

6.4 Bot / crawler làm ô nhiễm data

Case 8: Googlebot index trang → analytics tăng vọt

Googlebot mở trang, chạy JS, click link → SDK ghi 100 event/phút. Data team hoảng "traffic tăng đột biến!"

Cách xử: filter server-side hoặc client-side:

// Client-side check
if (navigator.webdriver || /bot|crawler|spider/i.test(navigator.userAgent)) {
    return;  // Không init SDK cho bot
}

Hoặc BE reject request có User-Agent match bot pattern.

6.5 Prerender preview (Chrome speculation)

Chrome 120+ hỗ trợ speculationrules: render sẵn trang link trước khi user click, để mở nhanh.

<script type="speculationrules">
  { "prerender": [{ "urls": ["/products"] }] }
</script>

User chưa click nhưng browser đã render /products → SDK fire screen_viewed giả.

// Cách check
if (document.prerendering) {
    // Đừng track — đợi 'prerenderingchange' event
    document.addEventListener('prerenderingchange', initTracking);
} else {
    initTracking();
}

6.6 Tab background 24 giờ

User mở tab, minimize browser, để 1 ngày. Khi visible lại:

  • document.visibilityState đổi từ hidden → visible
  • SDK check timeout → session_id đã idle > 30 phút → rotate → session mới
  • Event tiếp theo stamp session_id mới

6.7 Cross-tab session sync

Tab 1: app.com/products · Tab 2: app.com/cart

User tap ở Tab 1 lúc 14:00 → Tab 1 update last_active = 14:00 trong localStorage.
Tab 2 idle. Lúc 14:29 user tap Tab 2 → Tab 2 đọc localStorage → thấy last_active = 14:00, mới 29 phút → chưa timeout → dùng session cũ. ✅

6.8 Duplicate SDK load

App code import SDK 2 lần (accidentally, hoặc do bundle chain):

// index.html — 2 lần include, sai lầm phổ biến
<script src="unitrack.iife.js"></script>
<script src="unitrack.iife.js"></script>  ← Duplicate!

SDK sẽ 2 lần patch history.pushState → mỗi navigation fire 2 event. UniTrack có initialize() idempotent guard (biến installed = true) nên chỉ install 1 lần.

6.9 Time skew user machine

User set giờ máy sai (offset 3 tiếng). SDK dùng Date.now() stamp event timestamp → BE nhận thấy event từ 3 tiếng trước.

Cách xử: BE stamp received_at khi nhận request (như endpoint /web-events đã làm).

6.10 Server bị spike bởi analytics

Peak time: 10.000 user online × 100 event/user = 1M event/phút. Nếu SDK POST mỗi event riêng → 1M request/phút → BE chết.

Cách xử: batch. SDK gom 10 event thành 1 POST → chỉ 100k req/phút.

6.11 Localhost development bắn lên prod

Dev quên đổi endpoint khi build → data test bơm vào prod database. 
// Config theo NODE_ENV
UniTrack.initialize(apiKey, {
  endpoint: process.env.NODE_ENV === 'production'
    ? 'https://prod.com/events'
    : 'http://localhost:9090/events',
});

6.12 Version pin & cache stale

User giữ tab mở suốt 3 tuần. SDK bundle được cache. BE endpoint đổi shape v2 → SDK cũ vẫn gửi v1 shape → BE reject.

Cách xử: version trong URL:

<script src="/assets/js/unitrack.iife.v0.1.0.js"></script>

7. Privacy + PII + GDPR — pháp lý

7.1 PII vô tình lọt qua auto-capture

Case 9: URL query chứa email

Trang login sau redirect có URL:

https://app.com/dashboard?user=abc@example.com&token=xyz

SDK auto-capture screen_viewed → props chứa full URL → email lên analytics!

Cách xử: SDK dùng stripQuery() — chỉ giữ path, drop query string:

screen_viewed { screen: "/dashboard" }  ← ✅ đã strip query
Google từng bị FTC phạt vì log query string chứa credit card. GDPR fine cho leak email lên analytics: €20 million hoặc 4% revenue.

7.2 GDPR — Consent banner

EU yêu cầu website phải xin consent trước khi tracking. Flow:

User vào trang lần đầu
    ↓
Show banner: "Cho phép cookies để cải thiện trải nghiệm?"
    ↓
    ├─ [Accept] → localStorage.setItem('consent', 'accepted')
    │             UniTrack.initialize(...)
    │
    └─ [Decline] → localStorage.setItem('consent', 'denied')
                   SDK KHÔNG init, không track
UniTrack không tự xử consent — vì mỗi app có yêu cầu compliance khác nhau. App phải:
  • Show banner riêng
  • Chỉ gọi UniTrack.initialize() khi user accept
  • Provide button "Withdraw consent" — khi user click → gọi UniTrack.reset() + clear localStorage

7.3 PII hashing — best practice

Nếu bắt buộc track user_id/phone/email → hash trước khi gửi:

// SDK tự làm khi bro identify()
await UniTrack.identify("user@example.com");
// Backend nhận: user_id = "a3f5e2..." (SHA-256 hash)

Server không thể reverse hash → GDPR chấp nhận vì email raw không rời client.

7.4 form input value — KHÔNG bao giờ capture

UniTrack (và mọi tracker tử tế) KHÔNG capture <input> value. Chỉ ghi element_key (id/label). Nếu bro cần track "user điền form" → chỉ ghi form_submitted event, không ghi giá trị. 
// ✅ Đúng
UniTrack.track('form_submitted', {
  form_id: 'signup',
  fields_filled: 5  ← chỉ số lượng, không giá trị
});

// ❌ Sai — nghiêm cấm
UniTrack.track('form_submitted', {
  email: form.email.value,
  password: form.password.value  ← password lên analytics = GDPR breach + đuổi việc
});

Trước khi cho website nào tracking thật, chạy đủ checklist sau:

Browser matrix

  • ✅ Chrome (95% user desktop)
  • ✅ Firefox
  • ✅ Safari desktop
  • ✅ Edge
  • ✅ iOS Safari (WebKit khác, ITP)
  • ✅ Chrome Android

Session behavior

  • ✅ Reload page → session_id giữ nguyên
  • ✅ Mở 2 tab cùng URL → cùng session_id (localStorage cross-tab)
  • ✅ Đợi 31 phút idle → tap → session_id rotate, index +1
  • ✅ Click UniTrack.rotateSession() → manual rotate
  • ✅ Incognito mode → session sinh mới mỗi lần

Auto-capture

  • ✅ Tap button có data-track-id → event_key = data-track-id
  • ✅ Tap span text bên trong card → SDK resolve lên card ancestor
  • ✅ Right-click / Cmd+click không fire click event
  • ✅ SPA route change (React Router push) → screen_viewed fire
  • ✅ Hash routing (/#/page) → screen_viewed fire
  • ✅ Back button → screen_viewed fire

Network

  • ✅ fetch với host in allowlist → có header traceparent
  • ✅ fetch với host ngoài allowlist → KHÔNG có header
  • ✅ POST đến endpoint SDK → KHÔNG bị track (exclude self)
  • ✅ Request 404 → fire network_error
  • ✅ Request cancel qua AbortController → không crash SDK

Ops

  • ✅ AdBlock (uBlock Origin) enabled → SDK vẫn hoạt động (same-domain)
  • ✅ Offline → tap → back online → queue flush
  • ✅ Page unload (close tab) → sendBeacon flush
  • ✅ Bot user-agent → SDK skip (nếu có filter)
  • ✅ Duplicate script load → 1 event/tap, không 2

Privacy

  • ✅ URL có ?email=… → screen_viewed chỉ có path, không query
  • ✅ input value không xuất hiện trong bất kỳ event nào
  • ✅ Consent banner block SDK init đến khi accept
  • ✅ identify() → user_id ở BE là hashed, không raw
