🎫 KHI NÀO SINH TRACKING_ID MỚI?
① Cold start — app mở lần đầu sau cài / kill
② Timeout 30 phút — user idle quá lâu, session cũ chết
③ Manual rotate — gọi UniTrack.rotateSession() khi logout / switch account
🔬 CƠ CHẾ SINH
Chuẩn UUID v4 RFC 4122 — 122 bit random từ std::random_device + 6 bit cố định (version + variant).
Persist vào session.json trong app sandbox · 1:1 với session_id.
Resume cùng tracking_id nếu session chưa timeout.

📢 SCRIPT — 75 GIÂY

Tracking_id sinh ra khi nào? 3 trường hợp: cold start (lần mở đầu sau cài / kill app), timeout 30 phút inactivity, hoặc manual khi logout.

Cơ chế sinh: chuẩn UUID v4 RFC 4122 — 122 bit random, đảm bảo unique toàn cầu. Persist vào file session.json trong app sandbox, 1:1 với session_id. Nếu user mở app lại trong 30 phút, dùng lại cùng tracking_id.

Sau khi sinh, SDK tự stamp vào property của mọi event trước khi đẩy Snowplow. Bên phải là payload thật — session_id + tracking_id nằm trong data. Đây là chìa khoá để tra cứu ở slide cuối.

Slide trước tôi tóm 3 layer cho dễ hiểu. Bây giờ tôi zoom-in thành 8 layer thật — chính là kiến trúc observability chuẩn theo OpenTelemetry mà big tech đang dùng.

L1 Client — Mobile app + SDK + trace_id. UniTrack đã đóng xong cái này. Slot Local AI agents tôi để mở — đây là roadmap edge inference trên device, không cần lên cloud.

L2 Edge — API Gateway phải đón traceparent header từ mobile. Đây là cửa ngõ duy nhất, nếu L2 mất trace thì cả pipeline đứt.

L3 Backend services — mỗi microservice cần OTel SDK để tự sinh span cùng trace_id. Với service legacy không thay được code, ta dùng Service mesh sidecar — Istio hoặc Linkerd — sidecar tự bơm trace context.

L4 Data — DB, Cache, Message queue cũng phải truyền trace context. Postgres có extension log query với trace_id. Redis/Kafka có header passthrough.

L5 Telemetry pipeline — OTel Collector ngồi giữa. Nhận trace từ mọi layer, sampling, normalize schema, route sang storage. Không có L5 thì storage sẽ ngập với data raw.

L6 Storage — 3 store riêng biệt: Traces (Jaeger/Tempo), Logs (Loki/Elasticsearch), Metrics (Prometheus). Plus 1 Service catalog mô tả service nào do team nào quản lý — quan trọng cho L7.

L7 AI Intelligence — mới là phần đột phá. 4 agent: Root agent điều phối. Correlator map trace ↔ log ↔ metric ↔ service catalog. Anomaly + RCA phát hiện bất thường và tự giải thích nguyên nhân gốc. Report agent sinh báo cáo cho ISC.

L8 Output — đây là chỗ ISC tương tác: Dashboard (portal hôm nay đã có), Alerts vào đúng channel team, Auto-tickets tự fire vào Jira/Linear khi L7 detect issue.

Đây là bài toán dài hơi. UniTrack hôm nay đã đóng L1. Phần còn lại tôi sẽ xin 3 hướng góp ý cụ thể ở slide kế.
